## 8. Pipeline de eventos

**Hooks ligados** (`.claude/settings.json`, os 17 a correr `node "${CLAUDE_PROJECT_DIR}/hooks/log-event.mjs"` com `timeout` 10 s — 5 s em `SessionEnd`, que tem um orçamento de 1,5 s —, que lê o payload JSON do stdin e acrescenta uma linha a `data/events.jsonl`): `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `PermissionDenied`, `Notification`, `SubagentStart`, `SubagentStop`, `Stop`, `StopFailure`, `PreCompact`, `PostCompact`, `PreModelSwitch`, `PostModelSwitch`, `SessionEnd`. O hook nunca devolve JSON nem código 2, por isso nunca bloqueia nem altera uma decisão de permissão.

**Contrato do hook:** nunca bloqueia nem atrasa o Claude Code — saída sempre 0, tudo dentro de `try`, erros próprios em `data/hook-errors.log`; cada linha é `{ ts, project, ...payload }` com `ts` = hora ISO de captura (o payload não traz hora), `project = basename(cwd)`; `tool_input` e `tool_response` cortados a 16 KB cada (marca `_truncated: { field, original_length }`; o transcript do Claude Code guarda sempre o original); `cwd` normalizado (caixa da letra da drive, separadores) só para efeitos de chave; rotação quando o ficheiro passa de 64 MB (rename para `events.<ts>.jsonl`, ficheiro novo começa vazio). Uma escrita = um `appendFileSync` de uma linha completa (o NTFS serializa escritas em append; um hook concorrente nunca intercala meia linha).

**Redutor de estado** (`viewer/lib/state.mjs`, função pura sobre a sequência de eventos, corrida no servidor; testada com fixtures em `test/`): agrupa por run (chave = `run_id` dos eventos `Forja`, senão `session_id`), constrói instâncias por `agent_id`, liga cada instância à chamada `Agent` que a lançou (por `tool_response.agentId`; provisoriamente, por `PreToolUse(Agent)` seguido do `SubagentStart` do mesmo `subagent_type` na mesma sessão), e daí tira a task (`description`), o modelo pedido (`tool_input.model`) e o modelo real (`resolvedModel`). Continua a ler as linhas `Forja` históricas do fluxo legado (tasks, decisões, fila, veredictos, pausas), para que um `data/events.jsonl` antigo se reproduza igual na página de sessões `/legacy`; nenhum comando atual as escreve.

**Vitalidade é evidência, nunca "vi Start e não vi Stop".** Idade do último evento sob o `agent_id` (qualquer evento: Pre/PostToolUse dentro do subagente contam) ou sob a sessão principal:

| Estado (UI) | Regra |
|---|---|
| inativo | papel sem nenhuma instância neste run |
| a trabalhar | último evento há ≤ 90 s, sem fim conhecido |
| a trabalhar · silêncio há Xs | 90 s – 5 min sem evento (sinal âmbar visível; pensar longo é normal) |
| à espera de review | evento histórico `task.review` ainda sem veredicto |
| bloqueado | evento histórico `task.block`, ou `Notification` de permissão pendente (motivo mostrado) |
| precisa do Sponsor | pergunta aberta na fila histórica; ou sessão principal terminou o turno (`Stop`) com run ainda `running` |
| sem resposta | > 5 min sem evento e sem fim conhecido (subagente); > 10 min (sessão principal) |
| morto | > 30 min sem evento e sem fim conhecido, ou watchdog marcou |
| terminado | `SubagentStop`, ou `Agent` devolvido com `status: completed` para esse `agentId`, ou `SubagentHandback` seguido de silêncio > 90 s sem novo evento |
| falhou | `Agent` devolvido com status diferente de `completed`, ou `PostToolUseFailure` do `Agent`, ou evento histórico `task.fail` |
| em pausa | evento histórico `run.pause` (limite de utilização), até `run.unpause` |

O estado de um papel é o da sua instância mais relevante (bloqueado > a trabalhar > sem resposta > morto > à espera de review > falhou > terminado > inativo); com várias instâncias ativas, o cartão diz "N instâncias em paralelo" e lista-as. O estado do run é o mais alto entre: sessão fechada ou fim registado → terminado/falhou; sessão principal "precisa do Sponsor" ou "à espera de quota"; qualquer papel bloqueado; sessão principal morta / sem resposta / à espera de input; senão a trabalhar.

**Modo de falha → comportamento definido** (cada um tem uma fixture em `test/fixtures/` e um teste em `test/state.test.mjs`):

| Modo de falha | O que o redutor faz |
|---|---|
| `SubagentStop` nunca chega (subagente em background) | instância termina pelo resultado da chamada `Agent`, ou pelo `SubagentHandback` + 90 s de silêncio (marcada "inferido"); nunca "a trabalhar" para sempre |
| `SubagentStart` repetido para o mesmo `agent_id` (mensagem a subagente em background) | mesma instância, `startedAt` original, contador `reannounced`; só é instância nova se a anterior já terminou ou está morta (> 30 min sem evento) |
| `SubagentStop` sem `Start` e sem `duration_ms`, ou com `agent_type` vazio (compactação) | descartado; um segundo `Stop` para a mesma instância é ignorado |
| `SubagentStop` com `duration_ms` mas sem `Start` (hook de início perdido) | instância já terminada, início = `ts − duration_ms` |
| Entrega fora de ordem (resultado `Agent` antes do `Start`; `Stop` antes do último `PostToolUse` interno) | estado só usa `max()` de tempos e chaves estáveis (`agent_id`, `tool_use_id`); o `Start` real corrige o `startedAt` |
| Chamada `Agent` falha (`PostToolUseFailure`, ex. 429) | instância (se já existia) → falhou; erro com "rate limit / usage limit / quota / overloaded / 429 / 529" gera um sinal de fallback na linha do tempo |
| Permissão pedida (`PermissionRequest` ou `Notification permission_prompt`) | quem pediu fica **bloqueado** (subagente) ou **precisa do Sponsor** (sessão principal), com o motivo; limpa-se com `PermissionDenied` (contado), com o `PostToolUse` dessa ferramenta, ou com qualquer evento seguinte do mesmo ator |
| Permissão negada (`PermissionDenied`) | contador na instância e no run; entrada na linha do tempo |
| Recusa dura sem hook (modo headless `claude -p` com ferramentas recusadas não dispara `PermissionDenied` nem `PostToolUseFailure`) | um `PreToolUse` ainda sem `PostToolUse` quando o turno do ator termina (`Stop`, `SubagentHandback`, `SubagentStop`) conta como "recusada ou falhada": contador `refused`, entrada na linha do tempo. Nunca contado na `PreToolUse` seguinte, porque o Claude Code emite chamadas paralelas |
| Subagente cancelado (`TaskStop`; resultado `Agent` com `status` ≠ `completed`) | instância → falhou com o estado devolvido |
| Hook que falhou a escrever (linha em falta) | nada é inventado; o estado deriva do que existe; `data/hook-errors.log` guarda o erro do hook |
| Linha truncada ou corrompida, CRLF | contada em `badLines`, entrada "linha corrompida" na linha do tempo, ignorada; CRLF é aceite |
| Compactação (`PreCompact`/`PostCompact`) | contador `compactions`, entrada na linha do tempo; o `Stop` fantasma com `<analysis>` é descartado pela regra do `agent_type` vazio |
| Sessão principal termina o turno (`Stop`, `Notification idle_prompt`) com o run `running` | **precisa do Sponsor** (sessão principal e run); sem run: "à espera de input" |
| `StopFailure` | `rate_limit`/`overloaded` → "à espera de quota"; outros tipos → "precisa do Sponsor", com o tipo |
| `Notification quota_auto_resume_*` | `fired` limpa a espera; `stale`/`disabled` → "à espera de quota" com a instrução (Enter no terminal) |
| `PreModelSwitch`/`PostModelSwitch` | entrada na linha do tempo com de→para; o modelo mostrado por instância vem sempre do `resolvedModel` do resultado `Agent` |
| Sessão reiniciada / retomada (`SessionStart source: resume\|compact\|startup`) | a sessão nova junta-se ao mesmo run; instâncias abertas da sessão anterior ficam "terminado (sessão fechada)" no `SessionEnd` |
| `SessionEnd` | run terminado; instâncias abertas → "sessão fechada" |
| Dois runs em paralelo, vários projetos intercalados | runs separados por `run_id`/`session_id`; cada evento vai para o run da sua sessão; nada se mistura |
| `cwd` com caixa diferente / separadores (Windows) | chave de projeto normalizada (minúsculas, `/`); o run é o mesmo |
| Ferramentas nativas (`Explore`, `claude-code-guide`, …) e nomes históricos de papéis | nativas num grupo próprio; nomes históricos mapeados para os papéis do elenco histórico; instâncias nunca fundidas em contagens |

Nada inventa horas que o payload não trouxe.

## 9. UI (viewer)

Desenho em `docs/design/DESIGN.md`. Servidor `viewer/server.mjs` (Node core, sem dependências). A página principal (`/`, `/core`, `/m`, ficheiro `viewer/core.html`) é o painel Core: lê a projeção autenticada e só de leitura `/api/core` (`viewer/core-api.mjs`, a partir do `.forja/` de cada projeto registado e do `usage.jsonl` de cada run) e mostra tasks, invocações reais, validação, cobertura de utilização e decisões pendentes do Sponsor. Prompts, ficheiros de código e streams dos fornecedores nunca são expostos. A única escrita aceite é uma escolha explícita de tecnologia do Sponsor; arrancar, retomar e repetir um run Core continuam a ser operações da linha de comandos.

A página de sessões `/legacy` (e `/legacy/m`) mantém o feed de eventos-chave (`GET /feed`, `viewer/lib/feed.mjs`) e o estado reduzido enviado por Server-Sent Events (`/state`, `/events`) a partir de `data/events.jsonl`, incluindo runs históricos. O lançador de runs pelo telemóvel foi retirado na 0.22.0: `GET /projects` e `POST /runs` respondem 410 com uma indicação para a linha de comandos (`forja start`, `forja core resume`), depois da autenticação. Os projetos vêm sempre de `data/projects.json` (`lib/projects.mjs`), que também alimenta a guarda e o `forja projects list|prune`; o formato do registo não muda.

## 10. Notifications (ntfy)

Notification destinations are local configuration: `FORJA_NTFY_TOPIC` takes precedence over ignored `data/notify-config.json` (`{"topic":"your-topic"}`). Without a destination, the client returns `skipped: not-configured` and makes no network request. An explicitly empty environment value disables a configured topic.

Messages carry brief status only: never code, diffs, file contents, full paths, credentials or personal conversation history. Viewer links pass through `sanitizeClick`, which accepts HTTP(S) and strips user information, query parameters and fragments. The viewer still requires authentication.

Notifications are reserved for actionable intervention: open questions, blocked work requiring a decision, quota exhaustion, and supervisor abandonment after its bounded recovery attempts. Routine successful completion does not require a notification. Delivery failures are logged locally and never fail the run. Repeated successful messages are deduplicated for ten minutes.

## 11. Telemóvel

`forja up` arranca o viewer com token obrigatório: **página de entrada** na primeira visita a `/` ou `/m` — um formulário onde se cola o token uma vez, `POST /login`, cookie `forja_k` `HttpOnly` `SameSite=Lax`, **30 dias** e com `Secure` sempre que a visita não é loopback (`X-Forwarded-Proto: https` do cloudflared, ou um `Host` que não é 127.0.0.1/localhost). A submissão do próprio formulário chega com `Origin: null` (a página manda `Referrer-Policy: no-referrer`), por isso `POST /login` aceita `Origin: null` e a ausência de origem — o token é a própria prova — e continua a recusar a origem de outro site. Token errado dá a mesma página sem detalhes e com 1 s de atraso, no máximo 5 falhas por minuto, 429 depois; o token certo é validado **antes** de se consultar o travão, porque atrás do túnel todos os pedidos chegam do mesmo endereço. `?k=<token>` continua a funcionar; todas as outras rotas sem cookie são 401. Token em `data/viewer-token.txt`; `forja token rotate` gera outro e é a única forma de revogar um. **Nada imprime o token**: o arranque mostra só o endereço local e onde está o ficheiro, e `forja token` responde com o caminho, não com o segredo — a saída destes comandos é capturada pelo hook para `data/events.jsonl`.

O `up` abre um túnel gratuito e sem conta (Cloudflare quick tunnel com `cloudflared` portátil em `tools/cloudflared/`, pasta ignorada pelo git), lê a URL pública, envia-a por ntfy com `Click`, e vigia os dois processos (reinício com backoff; URL nova → ntfy outra vez). Como o endereço do túnel muda a cada arranque e o cookie é por endereço, o token cola-se uma vez por link novo. `forja autostart install` põe os atalhos do viewer e da guarda na pasta Arranque do Windows. O viewer nunca aceita `Host` fora da lista permitida (loopback + hostname do túnel atual) — proteção contra DNS rebinding — e nunca escreve fora de `forja/data/`. `forja down` para o viewer e o túnel e **nunca mata um controlador Core**: enumera a árvore de processos do `up`, tira do plano qualquer controlador Core e tudo o que está por baixo dele, e mata o resto do mais fundo para o mais à superfície.

## 12. Resiliência

- **Estado em disco:** o estado de um run Core vive em `.forja/` do projeto; um controlador que morre é retomado com `forja core resume` (à mão ou pela guarda). Nada depende da memória de uma conversa.
- **Watchdog** (dentro de `viewer/server.mjs`, a cada 30 s, sobre o mesmo redutor que a UI usa — uma única definição dos estados): instância "morto" (> 30 min) → ntfy, só enquanto quem a lançou ainda pode agir — um subagente sem sinal cuja sessão terminou (`SessionEnd`) ou cujo run histórico já fechou passa a histórico ("terminado", inferido) e não avisa; também não avisa quando a sessão principal já foi dada como morta (um só alerta por sessão) nem, num projeto com um run Core `running`/`blocked`, para sessões sem run ativo; quando o run Core do projeto acaba (`done`, falhado ou abandonado), uma sessão cujo último sinal de vida é anterior a esse fim (a conversa que lançou o run, sessões de worker acabadas ou paradas) continua sem avisar — o fim do run não a torna morta —, e só uma sessão com atividade depois do fim que fique calada volta a avisar (`coreProjectRuns` em `viewer/core-api.mjs` dá o estado e a hora de fim de cada run Core; issue #28, `test/watchdog-core-transition.test.mjs`); uma sessão principal morta avisa uma só vez por projeto: várias sessões caladas do mesmo projeto dão uma única notificação, que fala da mais recente e não se repete nas voltas seguintes; sessão principal "precisa do Sponsor" (turno terminado com run em curso, permissão pendente há > 2 min) → ntfy. Cada pedido de permissão avisa uma só vez e a mensagem leva só o estado e o nome da ferramenta, nunca o comando, URL ou pesquisa. Sessão principal "sem resposta" (> 10 min) e run "à espera de quota" **não** avisam o telemóvel (regra do Sponsor, 18 set 2026): os dois podem ainda recuperar sozinhos. O watchdog não reinicia processos; quem relança é a guarda.
- **Guarda dos controladores Core** (`forja guard [run] [--poll-ms N]|stop|status`; `lib/guard.mjs`, `data/guard/`): um **processo à parte**, com o seu próprio arranque automático no login (`forja-guard.vbs` + `forja-guard.cmd`, `forja autostart install`), e a única peça que **relança** alguma coisa. De 60 em 60 s lê o registo de projetos (`data/projects.json`) e o estado Core de cada um (`.forja/`, através de `lib/core/observe.mjs`) e corre `forja core resume --expected-run <id>` (`launchCore`, `lib/spawn-runner.mjs`, destacado e fora da árvore de processos de quem o lança) quando **tudo** isto se verifica: o run Core está `running`, o controlador e o worker estão mortos **há mais de 2 min**, a última tentativa foi **há mais de 15 min** e ainda não foram dadas **3 tentativas**. Tudo o resto é uma não-ação com motivo escrito em `data/guard/guard.log`: um run `blocked` ou terminado **nunca** é relançado (quem desbloqueia é uma pessoa, com `forja core retry`), nem um lock ilegível, nem um dono ou worker vivo. Só um run Core é relançado: um `docs/forja/RUN.json` legado é histórico, mesmo que diga `running`. Uma tentativa em que o spawn não deu pid não gasta uma das três tentativas reais mas é contada à parte (`failed_spawns`) e carimba a hora: o teto de 3 é sobre a soma. O contador vive em `data/guard/state.json` (escrita tmp+rename), atravessa reinícios da guarda e só se zera por prova positiva: `run_id` confirmado diferente, estado confirmado fora de `running`, ou controlador vivo **30 min seguidos**. Um `run_id` fora da forma `/^[A-Za-z0-9._-]{1,64}$/` é tratado como ilegível: sem ação, sem reset, e nunca é repetido no log nem numa notificação. O mapa de projetos do estado é criado sem protótipo (`Object.create(null)`). Um estado que não se lê nesta volta **não zera nada**. Notificação só com estado (nome do projeto e contagem): «desisti … precisa de ti», prioridade urgente, uma só vez por desistência; um relançamento que resulte não notifica (regra do Sponsor, 18 set 2026). A guarda não escreve em `data/events.jsonl` e não mata nada — `forja guard stop` escreve `data/guard/guard.stop` e a guarda sai na volta seguinte; uma segunda guarda no mesmo `data/` recusa com código 3 (lock em `data/guard/guard.lock.json`, helpers em `lib/process-lock.mjs`). O watchdog do viewer continua a avisar por si, em paralelo: são duas camadas independentes.
- **Supervisão mútua** (`lib/supervise.mjs`, `data/guard/state.json` chave `up` + `data/up-watch/`): a guarda e o viewer vigiam-se **um ao outro**, com as mesmas regras e constantes escritas uma vez só em `lib/supervise.mjs`: a guarda olha para o viewer na sua volta de **60 s** (`data/up.pid` + a linha de comandos do pid, `upAlive`) e o viewer olha para a guarda na sua volta de **30 s** (`peerCheck`, o lock `data/guard/guard.lock.json` com batimento com menos de 15 min + a linha de comandos, `guardProcessAlive`). Números iguais dos dois lados: **2 min** de graça antes de um par contar como morto, **3 tentativas** no máximo, **15 min** entre tentativas, e o contador só volta a zero com **30 min de saúde observada**. O estado vive em `data/guard/state.json` na chave **`up`, irmã de `projects`** (nunca lá dentro: um projeto pode chamar-se "up") e em `data/up-watch/state.json` na chave `guard`, ambos com escrita tmp+rename; os logs são `data/guard/guard.log` e `data/up-watch/up-watch.log`. Um relançamento que resulte não notifica; só a desistência, urgente e uma vez só, avisa o telemóvel.
  **Porque não oscila:** (1) na **dúvida o par está vivo** — uma linha de comandos que não se consegue ler nunca produz um relançamento; (2) nada é relançado antes de ter sido **visto vivo** uma vez (`seen_at`); (3) a graça de 2 min conta-se **sempre do arranque do próprio vigia** e um `dead_since` anterior a esse instante é ignorado, para um processo acabado de relançar não relançar de volta quem o relançou; (4) o teto de 3, com a desistência anunciada uma vez. Os **ficheiros de paragem ganham a tudo**: enquanto `data/up.stop` existir a guarda nunca relança o viewer, enquanto `data/guard/guard.stop` existir o viewer nunca relança a guarda — `forja down` continua a querer dizer «parado», e `forja autostart remove` (que escreve `guard.stop` e corre `down`) para tudo. Um `forja up` novo apaga o `up.stop` ao arrancar, mas volta a lê-lo **depois de chegar ao `listening`** e, se o ficheiro existir, sai sem escrever `up.pid` nem abrir o túnel: um pedido de paragem escrito enquanto ele arrancava ganha. Quem lança um par usa o intermediário destacado `launchForja` (`lib/spawn-runner.mjs`), para uma guarda lançada pelo viewer não ficar na árvore do viewer. O `startPeerWatch` do viewer é arrancado pelo `forja up` só depois do `listening` e do `up.pid` escrito; `FORJA_NO_PEER_WATCH=1` (ou `FORJA_NO_WATCHDOG=1`) desliga a vigia do lado do viewer.
  **Duas exigências do lado do viewer:** (a) a leitura da vida da guarda é **assíncrona** (`guardProcessAliveAsync`/`peerAliveCachedAsync`) — a versão síncrona passa por um `spawnSync` do PowerShell e parava o event loop que serve o SSE ~400 ms por volta; (b) a volta é **não reentrante** e encadeada com `setTimeout`, não `setInterval`, para duas voltas sobrepostas nunca relançarem as duas.
  **O que isto ainda não resolve:** se a guarda e o viewer morrerem **no mesmo instante e pela mesma causa** (máquina a suspender, logoff), a recuperação espera pelo arranque automático do login seguinte; um `forja up` relançado volta sempre na porta por omissão e com túnel; e um `forja serve` corrido à mão não escreve `up.pid`, por isso não conta como viewer (num data dir onde o `forja up` já correu, a guarda pode gastar as 3 tentativas a relançar um `up` que sai com porta ocupada).

## 13. Portabilidade

`node <forja>/bin/forja.mjs bootstrap <repo> [--dry-run]` faz o mesmo que `forja core init` corrido no repositório (preparação Core: bloco de instruções gerido, `.forja/` ignorado pelo Git, skills legadas de projetos antigos passadas a uso manual e agentes legados arquivados) e regista o projeto em `data/projects.json`. É idempotente e nunca reescreve conteúdo alheio. Valida-se em `examples/sample-project` (nunca num projeto real).

## Core observability and knowledge extension (21 September 2026)

Core registers projects through the existing registry. The authenticated read-only `/api/core` projection reads `.forja/current.json` and the run usage ledger; `/core` displays real tasks and invocations. Raw prompts, source files and provider streams are not exposed. Explicit Core start/retry remain CLI operations. Both `forja serve` and the existing up/guard services need to restart to load changed server code.

The guard recognizes driver `core`, uses the grace/retry/cap policy of §12 and launches `core resume --expected-run ID` outside the viewer process tree. It skips blocked/terminal state, live owner/worker and unreadable locks. The engine checks expected identity/status while holding its project lock. Viewer shutdown preserves Core executor subtrees.

Project knowledge is plain Markdown selected through `lib/core/knowledge.mjs`, optionally controlled by `docs/forja/KNOWLEDGE.json`. It is not imported from the personal Obsidian vault. The bounded in-memory sparse index provides line/hash references, optional source-dependency freshness checks and packet attribution. Details and limits: [selected knowledge in the Core runbook](CORE-RUNBOOK.md#conhecimento-selecionado).
