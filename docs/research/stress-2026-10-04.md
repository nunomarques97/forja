# Stress suite with the local profile (2026-10-04 run, measured 2026-10-05)

How far does FORJA Core get, unattended and with local models only, on 24 realistic small projects, and which failures belong to the pipeline rather than to the model? Results per scenario: [`test/stress/results/baseline.json`](../../test/stress/results/baseline.json), validated by `node test/stress/verify-results.mjs baseline`.

## Setup

- **Scenarios.** The 24 scenarios of [`test/stress/manifest.json`](../../test/stress/manifest.json) (8 categories, 3 each; 9 new projects, 15 unfamiliar codebases), built fresh from `test/stress/templates/` under `<lab>\stress\baseline\projects\` (`<lab>` is a lab folder outside this repository). Each has a hidden acceptance check in `test/stress/acceptance/`, run from this repository against the project after the run.
- **Profile.** [`config/core-local.json`](../../config/core-local.json): `qwen3-coder:30b-32k` through Kilo CLI 7.8.1 and Ollama 0.35.0 in plan, develop and review; per-call 8/15/8 minutes, `providerRetries: 1`, `maxCloudSessions: 0`. The harness caps each scenario at 8 sessions, 2 attempts and 25 minutes of wall clock (it kills the process tree) and removes cloud credentials from the nested environment. No Claude session was used by any nested run.
- **Run.** `node tools/stress-run.mjs run --detach` (sequential, resumable), 05:58–07:51 UTC on 2026-10-05, 113 active minutes, no GPU wait beyond the 4-second sampling, no scenario reached the 25-minute cap. `node tools/stress-run.mjs export` wrote the committed file from the lab results with local paths replaced by `<lab>`; the evidence of each scenario (`forja.log`, `change.diff`, `acceptance.log` and the run's `.forja/runs/<id>/call-N-*` files) stays in the lab folder.
- **Judging.** For every scenario I read the acceptance output, the saved diff and the run's call streams and ledger. `verdict` is the acceptance result (my reading agreed with it in all 24); `change` is my reading of the diff regardless of how FORJA ended (`correct`, `wrong`, `none`).

## Classification rule

Fixed after reading the first result and before judging the other 23:

- **pipeline**: the controller ended the run while budget for a recoverable step was left (an attempt, a result reminder, a provider retry), or it blocked a change that was correct, or a packet, plan, review, check or delivery defect caused the failure. The area names the controller part that ended the run.
- **model**: the model used its budget and produced wrong or no work while the pipeline behaved as designed.

One class per failure (the cause that ended the run); `failure.note` keeps a contributing model weakness. Under this rule every one of the 24 failures is pipeline: no run used its second attempt, its remaining sessions or its wall-clock budget, and each one stopped on the first structured-output problem of a local session. The `change` column shows how much of that is also a model weakness.

## What ended the runs

Three mechanisms, all after a local session returned something other than a valid result for its phase:

1. **Planner without a plan (12, planning).** The read-only planner (Kilo tools `glob`, `grep`, `read`, `webfetch`) tried 4 to 12 times to call `edit`, `write`, `bash`, `task` or `question`, then answered with a developer-style JSON (`{"status":"completed",...}` claiming a fix), a progress-notes-shaped JSON or prose with code. Kilo's result follow-up ran in 7 of the 12 (`result_follow_up` in the ledger, about 10 s) without producing a valid plan, and none was sent in the other 5; the controller blocked with "Plan must contain 1–30 cohesive tasks" on the first plan call with 7 sessions left.
2. **Developer status outside the enum or no result (6, recovery).** `"status": "completed"` (3 runs), prose without JSON after a correct second attempt (`failing-route-priority`), `{"error": "No active session to summarize"}` after Kilo's context compaction (`bug-csv-quoted`) and Kilo's "Compaction exhausted" provider error (`failing-month-math`). The controller blocks "Invalid/oversize worker result: unknown status" or a provider failure ("No automatic retry of provider failures") with one attempt of two unused. Two of these six blocked a correct change before review.
3. **Reviewer without a verdict (6, review).** `{"status":"done"}` instead of `approve`/`reject` (3 runs, the defect already seen in the bake-off), prose without JSON (2) and a textual `<function=read>` tool call that ended the Kilo session (1, "No automatic retry of review provider failures"). Three of these six blocked a correct change.

Model weaknesses behind them: the planner does not keep to its read-only role, the developer loops on details for 12–15 minutes (`""` escapes in CSV, local time against UTC) until Kilo compacts the context, and wrong or incomplete changes in 7 runs (left a declared dependency, missing trim, `.\` paths, junk files such as `Found`, `Next`, `test_normalize.mjs` and `progress-notes.md` in the project). Even with the pipeline fixed, those 7 would need the reviewer to reject and the second attempt to succeed.

The repository-map flag from the efficiency A/B (decision log, "eff-live-ab") is not triggered: no failure involved a file the map left out; planners and developers found and read the right files in all 24 runs.

## For the stress-fix task (candidates, not changed here)

- A phase result that does not match the phase (no tasks in a plan, a status outside the enum, `done` from a reviewer) gets one schema reminder in the same session, and if still invalid it costs an attempt instead of blocking the run while attempts remain.
- A local provider failure without a result (no final JSON, compaction exhausted) is retried once under `providerRetries` like other provider failures.
- The review result schema allows only `approve` and `reject`.
