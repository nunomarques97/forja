## 2026-10-04 — issue-36: worker staging and the occupied-index guard

Issue #36 was read with `gh issue view 36 -R nunomarques97/forja` (read-only). Its expected behaviour is implemented as written, with these choices:

- **Where.** The index is compared around each develop session inside the controller's `call` (only when `delivery` is configured), not when delivery is prepared. Checks, the manifest and the review then see a clean index, and the receipt's `originalIndex` binding is computed after the restore, so snapshot binding is unchanged. Runs without delivery keep today's behaviour (no Git index writes).
- **Restore only from a clean pre-session index.** "Restore to the pre-session state" is implemented as unstaging (`git restore --staged`) when nothing was staged before the session. When staged entries existed before, the controller leaves the index alone and delivery blocks as before; reconstructing a mixed pre-session index entry by entry was rejected as complexity without a reported need, since delivery refuses that state anyway.
- **Lossless test.** Every staged entry must equal the working tree (porcelain `git diff` after an in-memory stat refresh; a staged deletion requires the path to be absent on disk). Intent-to-add entries carry no content and are unstaged with the rest. Unmerged entries, staged-then-edited files and `git rm --cached` of a kept file are left staged and named.
- **Worker instruction.** The no-staging rule is added to the develop instruction of delivery runs only, not to docs/CORE.md: CORE.md is sent to every session, and the controller-side restore already makes the rule advisory. This keeps prompt growth out of runs that cannot be affected (efficiency goal).
- **Not covered.** A controller crash during a develop session loses the in-memory pre-session record; the next session then starts from the staged index and delivery blocks with the paths named (safe default, documented).

## 2026-10-04 — issue-36 (review fix): lossless test compares index rows

Review found that the porcelain `git diff` used as the lossless test ignores a staged mode when `core.fileMode=false` (the Windows default) and a staged link type when `core.symlinks=false`, so a worker's `git add --chmod=+x` or staged symlink was unstaged and then lost, because delivery stages from the working tree. The test now builds a scratch index the way delivery builds its candidate (HEAD plus a working-tree `git add` of the staged paths, in a temporary file outside the repository) and unstages only when every staged `ls-files --stage` row (mode, object) equals it. This supersedes the "Lossless test" bullet above. Entries that cannot be added from the working tree (a force-added ignored file, a staged new file missing on disk) are kept. The pre-session record also holds HEAD: if the session moved HEAD, the index is left exactly as the worker left it and the existing "changed Git HEAD" block applies.

## 2026-10-04 — eff-measure: how waste is measured

- **Two tools, both offline.** `tools/efficiency-audit.mjs` measures real runs from the files Core already writes; `tools/efficiency-bench.mjs` measures the controller's deterministic parts with scripted `drive()` runs (custom provider, no model call). No new run state or ledger field was added: `.forja` formats are unchanged.
- **Roots are arguments, not defaults.** The audit takes `--root` instead of built-in machine paths, because a personal home path in a versioned file is refused by the delivery privacy scan and would leak the machine layout of a public repository. Fixtures use neutral paths for the same reason.
- **Killed sessions are measured from their streams.** A develop session stopped at the context limit has `usage: null` in the ledger; the audit uses the stream's per-call request sizes for those rows (never both). Without this, 26.6% of input would be invisible and the largest waste would rank last.
- **Repeated context is compared by hash per part.** Instruction lines and top-level packet keys are hashed and compared within a run, so the audit can say what repeats without keeping any text; the benchmark uses the same function (`promptParts`) so offline and real numbers mean the same thing.
- **Benchmark numbers are normalized.** Temp root, run IDs, timestamps and durations are replaced before measuring, so the same source gives the same metrics and SHA-256 on every run and machine; `test/efficiency-bench.test.mjs` asserts this.
- **Ranking by share of input touched.** docs/EFFICIENCY.md ranks candidates by the measured share they could affect, not by ease. The top two (long high-context sessions, large tool outputs resent on every call) are outside the FORJA packet, which is 8.5% of context tokens; packet trimming candidates are listed with that ceiling stated.

## 2026-10-05 — eff-context: packet size and repeated context

- **Evidence from real packets, not only fixtures.** The benchmark fixtures are small, so a new read-only tool, `tools/efficiency-replay.mjs`, replays each candidate as a transform of the packets that real runs recorded and weighs the removed characters by the model calls of each session. Like the audit it prints aggregates only and takes its roots as arguments. The benchmark gained quality probes, review packet totals and a packets-only `wide-repo` fixture; this instrumentation left the scenario numbers unchanged (2,399,163 prompt characters) and was re-baselined before any candidate.
- **Keep rule.** A candidate is kept only with a measured size gain, every quality probe covering the removed information at 100%, and unchanged scenario outcomes. A size gain that removes information no probe shows to be redundant is a candidate "without measurable gain" for the stop rule: the goal asks for improvements in cost, speed or quality, not a cost gain bought with quality.
- **Kept: task packets use a 3,000-character repository map with the task files pinned first; the plan packet keeps 6,000.** Replay: 9.49% of packet resend, about 0.65% of all input, every task file still listed. A plain 3,000 cut (tried first) dropped 16% of the task files and was rejected. The plan keeps the larger map because planning explores the whole repository.
- **Rejected: criteria cap of 600 characters for overlapping remaining tasks** (78% of them would lose part of their criteria) and **no map in review packets** (gain 1.6% of packet resend, but no evidence the reviewer does not need it). Both were benchmarked as temporary edits and reverted; the cap stays 1,200. These two consecutive rejections ended iteration in this area.
- **Not tried:** the knowledge relevance cut (replay 0.10% of input) by the stop rule; goal and decisions (overall context of every task); large tool outputs (the largest context candidate) because its lever is the provider adapter and its quality guard needs a live run. Numbers in docs/EFFICIENCY.md.

## 2026-10-05 — local-provider: Ollama routes through the installed Kilo CLI

- **Route shape.** A local route is `{ "provider": "kilo", "localProvider": "ollama", "model": "<ollama tag>" }` for `plan`, `develop` or `review` (any tier). `model` is the plain Ollama tag; the adapter passes `--model ollama/<tag>`. The Codex OSS pilot (`provider: "codex"`) keeps its arguments and preflight unchanged. Reason: Codex is not installed here and nothing may be installed; Kilo 7.8.1 is. All options are free, so no Sponsor decision is needed.
- **No cloud path inside Kilo.** The local invocation adds to Kilo's inline config only the `ollama` provider (`@ai-sdk/openai-compatible`, bundled in Kilo, base URL fixed to `http://127.0.0.1:11434/v1`) and `enabled_providers: ["ollama"]`, and sets both `model` and `small_model` to the route model, so Kilo's auxiliary title call cannot pick a gateway model either. Verified: `kilo models` lists only the Ollama model with this config, 334 models without it. Permission policy, empty config home and disabled project config are the same as for gateway Kilo routes.
- **Context-window preflight for Kilo.** Evidence: with `qwen3:8b` (no `num_ctx` in its Modelfile) Ollama loaded the model with 4,096 tokens and silently truncated the prompt; the model answered "I'm ready to assist" without seeing the task. Kilo's own system prompt and tools are about 8,100 tokens. So Kilo local routes require a Modelfile `num_ctx` of at least 16,384 (read from `/api/show` `parameters`, no model load) and fail with a message that says so; the declared value is also passed to Kilo as the model's context limit. Not applied to the Codex pilot, to keep it unchanged.
- **Preflight errors name the cause.** Unreachable server (connection error code or 5-second timeout), HTTP error, model not installed, remote/cloud model (in the list or in its metadata), no tool support, too small context. All say FORJA does not download models or fall back to cloud; the run blocks with the `provider` code and the ledger records the call as local.
- **Doctor.** `core doctor` probes Ollama only when the profile has local routes, through `/api/tags` and `/api/show` (no model is loaded or invoked), and reports one check per route model with the routes that use it. `doctor()` stays synchronous for existing callers; the CLI uses the new async `doctorWithLocal`.
- **Effort.** `--variant` is passed through; Kilo accepted `--variant low` on an Ollama model without error. It has no documented effect on these models.
- **One result follow-up for local Kilo sessions.** Evidence from real FORJA runs in forja-lab: `qwen3-coder:30b-32k` (plan and develop) and `forja-gpt-oss:20b-32k` (plan) used tools correctly but ended with prose instead of the result JSON appended to the prompt, so the run blocked although the develop work was correct (fix and tests passing). A manual follow-up in the same session (`kilo run --session <id>`) with a short JSON-only reminder returned a valid result in 36 s. So when a local Kilo call exits cleanly without a final JSON and at least 15 s of the call time remain, the adapter sends that one reminder in the same session, with the same permissions and the remaining time; usage and calls of both processes are summed and the ledger records `result_follow_up`. Gateway (cloud) Kilo routes are unchanged, so no extra paid call is introduced. Rejected: a second retry or reparsing prose, because a result must still come from the model in the schema.

## 2026-10-05 — escalation: opt-in hand-off of local develop tasks to the Claude CLI route

- **Shape.** `escalation: { route: { provider: "claude", model?, effort?, maxMinutes? }, maxEscalations (1..10, default 1), attempts (1..5, default 1) }` in the profile, validated by `validateRouting` (so start, resume, queue and `core doctor` all refuse a bad one). The target is closed to `claude` without `localProvider` or `command`: it is the only path from local to cloud. A profile without a local develop route, or with `maxCloudSessions: 0`, is refused rather than silently ignoring the option.
- **Triggers, develop only.** Attempts exhausted on a local route, or a local develop session that ends with timeout, output budget, provider failure or an invalid result. Provider-failure triggers wait for the existing automatic fresh session (`providerRetries`), because a cheap local retry comes before a cloud session; an invalid result escalates at once (it never had a retry). Plan and review do not escalate, so the escalated work is still reviewed by the configured (local) reviewer. Usage limits, context rotations and `blocked` results are excluded: they are not local-model failures that a stronger model fixes.
- **Attempts.** The escalated task gets `attempts` on the Claude route on top of the ones spent locally (`attempt_limit` in task state, used by the loop and by `core retry`), instead of refunding the failed local attempt, so attempt counts stay truthful. The escalated limit replaces the run's `maxAttempts` (stored as `run_attempts` at hand-off); only a later explicit `--max-attempts` increase adds to it, so an early stuck escalation never runs more Claude sessions than `attempts` (review finding: with `maxAttempts` 3 a stuck session at attempt 1 had given two Claude attempts).
- **Ledger without a new row type.** The escalation is a field on the ledger row of the first escalated invocation, not a separate row: every ledger reader (usage, evidence, diagnose, lessons, viewer, efficiency tools) keys rows by invocation id, and a row without one would distort their counts. Run state keeps `escalations[]` and `task.escalation` (validated on load), which `core status` shows.
- **Subscription only.** Escalation is refused at run time when `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_BASE_URL` is set, the same environment rule as the benchmark provider; the message names the variable, never its value. The check runs at hand-off and again before every launch on the escalation route (resume or retry from another environment), as a pre-launch `provider` stop that spends no attempt. Tests use mock executors only; no real Claude escalation was run.

## 2026-10-05 — bakeoff: how local models are compared

- **One model in every phase per run.** Each bake-off run gives plan, develop and review to the same model, so only one model is loaded at a time (no swap between phases on a 16 GB card) and the role results come from the ledger of that run. A model whose own plan fails gets a second run of the same task with the task's fixed plan (`--plan`), so its developer and reviewer are still measured; that run never counts for the planner.
- **Correctness is a hidden acceptance test**, kept in `test/bakeoff/tasks/<id>/acceptance.test.mjs` and run from outside the scratch project after the run, plus the project's own `node --test` and my reading of the saved diff. The reviewer is judged by its last verdict against that acceptance result (approve on a passing change or reject on a failing one is correct). Each oracle is tested to fail on the untouched template and pass on a reference solution.
- **Screening then finalists.** Every candidate runs the quick `duration-fix` task; the three best (3 points for acceptance, 1 for a usable plan, 1 for a correct review verdict, time as tie-break) run the three full tasks. Caps: 6 sessions, 2 attempts, no provider retry, per-call 6/10/6 minutes (plan/develop/review), 20 or 25 minutes per run (the harness kills the process tree), 180 minutes of active harness time in total, `maxCloudSessions: 0`.
- **Context variants instead of new weights.** Installed models without a declared `num_ctx` get a `forja-bk-<base>:32k` variant (`/api/create` with `num_ctx 32768`, which only adds a manifest), because the Kilo preflight refuses a smaller context. Variants and pulled models are recorded in the results; `cleanup` removes only those, and keeps any model named in `config/core-local.json`.
- **Pulled models.** Three free, tool-capable models that fit 16 GB were added from the Ollama library: `devstral-small-2:24b` (15 GB, Apache 2.0), `qwen2.5-coder:14b` (9 GB, Apache 2.0) and `rnj-1:8b` (5.1 GB, Apache 2.0). Larger current coding models in the library (qwen3.6/qwen3.8 27B at 18 GB, north-mini-code at 19 GB, laguna-xs at 20 GB) were left out as they do not fit; cloud tags were excluded.
- **GPU courtesy.** Windows reports no per-process GPU memory, so "another process is using the GPU heavily" is measured as utilization of at least 40 % (median of three samples) or at least 6 GiB in use beyond what Ollama reports for its loaded models, or any non-candidate model loaded in Ollama. The harness waits (polling every minute, at most 60 minutes) before every probe and run.

## 2026-10-05 — eff-live-ab: live A/B of the kept efficiency changes

Because it rested on two discordant pairs, a third repeat was added within the 90-minute cap (62 minutes used); its three pairs were concordant and the verdict stayed "contradicts" (5 of 9 against 7 of 9). ## 2026-10-05 — stress-harness: manifest, scenarios and runner

- **Scenario layout.** A scenario is a base template (`test/stress/templates/<base>`, its own tests pass) plus overlays committed one by one with their own messages, so a regression scenario carries the commit that introduced it and the model can find it in `git log`. Two unfamiliar codebases (`tallybook`, a ledger CLI with conventions in its README; `routekit`, a request toolkit) are shared by several scenarios; small new projects have their own template. Rejected: one directory per scenario with the bug already in place, which loses the history regressions need and copies each codebase several times.
- **Hidden material outside the project.** Acceptance checks (`test/stress/acceptance/<id>.test.mjs`, `STRESS_PROJECT` names the project) and reference solutions (`test/stress/acceptance/solutions/<id>/`) are never copied; `build-scenarios.mjs` copies only `templates/`. `test/stress-manifest.test.mjs` builds every scenario and requires its check to fail untouched and pass with the reference solution.
- **What a check requires.** Where the goal says "add tests", the check requires at least one test more than the template had; where it forbids changing tests, it compares those files with the template. Ambiguous scenarios check only what the project fixes (for example `docs/STYLE.md`) or what any reasonable reading gives (per-client 429 with `Retry-After`), never one arbitrary choice.
- **Runner.** `tools/stress-run.mjs` follows the bake-off harness: sequential, detached, resumable, a STOP file, a 660-minute active cap per results set and a per-scenario cap (default 25 minutes) that kills the process tree, the same GPU courtesy rule. The profile is the given local profile with the scenario budgets as upper bounds and `maxCloudSessions: 0`; a profile with a non-Ollama route or an `escalation` block is refused before any run, and cloud credentials are removed from the nested environment. Results per label (`baseline`, `after`) live under the lab folder; committing an anonymized copy is the baseline task's job.

## 2026-10-05 — stress-baseline: how stress failures are judged and classified

- **Class = the cause that ended the run.** A failure is pipeline when the controller ended the run while budget for a recoverable step was left (attempt, result reminder, provider retry), blocked a correct change, or a packet, plan, review, check or delivery defect caused it; model when the model used its budget and produced wrong or no work while the pipeline behaved as designed. One class per failure; a contributing model weakness goes in `failure.note`. Fixed after the first result, before judging the other 23. Rejected: classing by "would the model have passed anyway", which needs a counterfactual run.
- **Outcome: 24 of 24 pipeline (12 planning, 6 review, 6 recovery), 0 completed.** Every run stopped on the first structured-output problem of a local session with attempts and sessions left; 5 of those blocked a change that passes the hidden check. Each record also carries `change` (correct, wrong, none) from my reading of the diff, so stress-fix can tell the 5 blocked correct changes from the 7 wrong ones.
- **Committed results are exported, not copied.** `tools/stress-run.mjs export` writes `test/stress/results/<label>.json` from the lab results with local paths replaced by `<lab>`, keeping verdict, change, judgement and failure already in the committed file, so a re-export after a resumed run never loses a judgement. `test/stress/verify-results.mjs` refuses a missing scenario, an unclassified failure, a pipeline failure without an area, a summary that does not match the records and any absolute local path.
- **Map flag not triggered.** No baseline failure involved a file the task-packet repository map left out, so the eff-live-ab map change stays.

## 2026-10-05 — stress-fix: pipeline fixes for the stress failures

- **Scope: local routes only.** Every change below applies when the route is local (`localProvider: "ollama"`); cloud routes keep their schemas, prompts and immediate stops, so no extra paid session can come from these fixes. Acceptance checks and scenarios are unchanged.
- **Phase-specific result contract for local sessions.** The local schema restricts `status` to the statuses of the phase (develop: done, ready_for_validation, blocked, checkpoint; review: approve, reject, blocked) and the prompt states the role of the phase next to the schema (`KILO_PHASE_ROLES`: the planner inspects and returns a plan, never implements; the reviewer returns approve or reject). Evidence: 12 baseline planners answered with a developer-style result, 3 reviewers with `done`.
- **Invalid final JSON gets the same-session reminder.** The one Kilo result follow-up now also runs when the final JSON exists but is not a result of its phase, and the reminder names the problem (`kiloInvalidResultReminder`). Before, it ran only when no JSON was found.
- **One fresh session instead of a block.** A local session that still ends without a usable result gets one fresh session of its phase under `providerRetries`: develop through `providerRetryDecision` (new code `result`; `provider` failures without a result, such as Kilo "Compaction exhausted", are now retried for local routes too), planning once per controller start, review once per validated tree (`task.review_retry`). A second failure blocks as before. This replaces the escalation entry's "an invalid result escalates at once": a local invalid result now gets its local retry first, then escalates when escalation is configured.
- **Local developers cannot move HEAD.** A pilot developer ran `git commit`, and "develop changed Git HEAD" blocked a change that passes its hidden check. The local develop Bash permission denies Git subcommands that rewrite history, the index or the working tree (`KILO_DEVELOP_BASH`, both `git <sub>` and `git <option> <sub>` forms); read-only Git still runs. Checked with Kilo 7.8.1 before relying on it.
- **A local plan that cannot fit the session budget becomes one task.** First rerun (5 scenarios, lab `after-a`): local planners split small bug fixes into inspect/fix/verify/test tasks; the first task already made the whole fix and the later ones exhausted the 8 sessions, so 3 of 5 runs blocked on the session budget, 2 of them with a change that passes the hidden check. Each task needs at least one develop and one review session, so when a local plan has more than one task and `2 × tasks > remaining sessions − 1`, the controller merges the tasks in dependency order into one (union of criteria, files, risks and checks with identical checks once, highest complexity, `merged_from` in task state) and logs it. Rejected: refusing the plan and asking again (one more local planning session that the baseline shows is often ignored), normalizing numeric task IDs (the only such plan also had prose checks and string criteria, a model failure), and applying the merge to cloud routes (their budgets are larger and users raise them explicitly).
- **A local plan or review timeout gets the same fresh session.** Second rerun, `bug-lru-recency`: the local planner spent its 8 minutes on 7 web fetches, refused edit/bash/question calls and rereads, and the run stopped on the plan timeout with 7 sessions left. A timed-out local plan or review session has returned no usable result like the cases above, so it now takes the one fresh session of its phase (same budget: once per controller start for planning, once per validated tree for review); cloud plan and review timeouts still stop at once. Not changed: the planner's web access (one run's evidence).
- **An off-schema local plan is told every wrong field at once.** `failing-slugify` (second rerun) and `bug-lru-recency` (first rerun): the planner invented its own task shape twice in a row (numeric IDs, text criteria, prose checks, `after` as a sentence, complexity `Low`). The reminder and the fresh planning session named only the first problem validatePlan meets ("Invalid or duplicate task ID."), so the second plan repeated the rest. The plan problem now appends one sentence listing every task field shape that is wrong (`planShapeProblems`), at most about 420 characters; the reminder keeps up to 600 characters of the problem. Rejected: normalizing such a plan in the controller (prose checks cannot become executable commands).
