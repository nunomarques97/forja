## Phase 5, WU-C — local live events viewer (2026-09-15)

**Built:** `viewer/server.mjs` (Node core only, no dependencies) serves `viewer/index.html` on http://127.0.0.1:4317 and streams `data/events.jsonl` over Server-Sent Events. Start: `node viewer/server.mjs`. Test: `npm run test:viewer` (14/14, runs against a temp file).

**Live or reload:** live, no reload. The server checks the file's size every 500 ms (`fs.watchFile`) and pushes each newly completed line to every open page. New rows can lag by up to ~500 ms. This is polling on the server, not OS file-change notification.

**Data findings:**
- Source project: `log-event.mjs` adds `project = basename(payload.cwd)`; the raw `cwd` is also on every line. Two repos with the same folder name would merge, and a session whose cwd is a subfolder would show the subfolder name.
- Reviewer vs main session: `agent_type` / `agent_id` are present only on subagent events.
- Synthetic events: lines with `session_id: "test-session-id"` come from `hooks/test-log-event.mjs` and are labelled project `forja`, although forja has no hook wired. Lines 1 and 16–19 are synthetic (16–19 were added by the screenshot runs of this task).

**Screenshots** (`docs/screenshots/`, real headless Chrome driven over CDP, one tab, no reload):
- `wu-c-1-initial-1440.png`: current contents (18 events).
- `wu-c-2-after-new-event-1440.png`: after `node hooks/test-log-event.mjs`, row 19 (`2026-09-15T20:30:59.541Z forja Read`) appeared highlighted. Same page: marker set before the event was still present, navigation count 1, same `timeOrigin`.
- `wu-c-4-new-event-expanded-1440.png`: full raw record of row 19.

**Reviewer (Agent Teams, `reviewer` subagent):**
1. **REJECT.** Blocking: DNS rebinding. The server did not check the `Host` header, so `curl -H "Host: evil.example:4317" http://127.0.0.1:4317/events` returned the full stream. Fix: 403 unless Host is exactly `127.0.0.1:<port>` or `localhost:<port>`, plus a test; README wording changed to state the 500 ms polling.
2. **APPROVE** after the fix. Tests 14/14; foreign Host, uppercase, trailing dot, `[::1]`, missing port, wrong port and suffix attacks all refused; scope limited to forja files; no dependencies.

**Deferred (non-blocking, from the Reviewer):** truncate-and-regrow within one 500 ms poll is missed; project filter may reset to "all" after a reconnect; key fields of non-PostToolUse events only show in the expanded record; each connection reads the whole file; Host bypass variants tested by hand only, not in the suite.

Nó deixa de dizer "running" para sempre.** Duas constantes novas em `viewer/index.html`, com propósitos deliberadamente diferentes (ver comentário completo no código): `STALE_MS = 5 min` — puramente de apresentação, decide quando um nó deixa de reivindicar "running" e passa a um estado visualmente distinto ("no response", cinzento, mesmo token `--muted` de qualquer outro "não temos a certeza" nesta app); justificado pelo maior intervalo real entre dois eventos dentro de uma chamada bem pareada nos dados reais (95.6s) — 5 min dá margem confortável sem arriscar apanhar uma chamada genuinamente só a pensar. `computeModelStats()` passou a registar `lastActivityTs` por `agent_id` aberto, atualizado por QUALQUER evento sob esse id (não só Start/Stop — `PreToolUse`/`PostToolUse` dentro do próprio subagente contam), para distinguir "ainda a trabalhar, só o hook de fecho é que falha" de "o hook de fecho nunca vai chegar". `tickTimers()` corre a cada segundo e alterna as classes `active`/`stale` do nó (CSS movida de `style="stroke:${color}"` inline para `var(--c)`, para a mudança de estado ser só uma troca de classe, sem tocar em `style` por elemento). Log de chamadas e painel "selected handoff" também deixam de dizer "live"/"still running" para uma chamada nestas condições — a mesma verdade em todos os sítios, não um grafo a dizer uma coisa e um painel a dizer outra.

### Falhas silenciosas encontradas (por área)

**Pipeline de eventos (5.1)**
1. `hooks/log-event.mjs` não é à prova de falha: `mkdirSync`/`appendFileSync` estão fora do `try` — um disco cheio, um `EBUSY` ou uma pasta sem permissão rebenta o processo com saída não-zero e barulho no terminal do Claude Code. Não há registo de erros do próprio hook.

## Sessão de hardening — Fase 2: achados empíricos sobre o Claude Code (16 set 2026)

Verificado nesta máquina (Claude Code 2.1.263), com sessões filhas `claude -p` lançadas a partir desta sessão e hooks apontados ao `hooks/log-event.mjs` do Forja via caminho absoluto:

- **Uma sessão filha `claude -p` corre dentro de uma sessão do Claude Code** (com ou sem as variáveis `CLAUDECODE`/`CLAUDE_CODE_SESSION_ID` no ambiente) e os hooks disparam normalmente para o stream global: `SessionStart` (`source: startup`), `UserPromptSubmit`, `PreToolUse`/`PostToolUse`, `Stop`, `SessionEnd` (`reason: other`); o ponteiro `data/sessions/<chave>.json` é escrito. É assim que o dogfood da fase 6 corre (sessão nova, com os agentes de nome de forja carregados).
- **Em `--permission-mode auto`, uma escrita de ficheiro por Bash é permitida sem pedido**; nenhum `PermissionRequest`/`Notification` dispara.
- **Uma recusa dura (`--disallowedTools "Bash(rm:*)"`) não dispara `PermissionDenied` nem `PostToolUseFailure`**: o único rasto é um `PreToolUse` sem `PostToolUse`, seguido do fim do turno. O redutor passou a contar isto como "recusada ou falhada" no fecho do turno de cada ator (`Stop`, `SubagentHandback`, `SubagentStop`), nunca na `PreToolUse` seguinte, porque o Claude Code emite chamadas em paralelo (fixture `denied-headless`, teste correspondente).
- **Em modo `auto` o modelo pode recusar por si próprio um comando destrutivo** (`rm -rf`) sem sequer chamar a ferramenta — nesse caso não há evento nenhum além do `Stop`.
- **Cloudflare quick tunnel** (binário portátil `tools/cloudflared/cloudflared.exe`, versão 2026.9.1): a URL pública chega ~7 s depois do arranque (a linha "Requesting new quick Tunnel on trycloudflare.com…" aparece antes e não é a URL); através da URL pública o viewer devolveu 403 até o hostname estar em `data/tunnel.json`, depois 302 com cookie ao primeiro pedido com `?k=<token>` e 200 com o estado real. Um `curl` de 3 s ao `/events` (SSE) pela URL pública não trouxe bytes — as páginas fazem fallback para polling de `/state` se não receberem `state` por SSE em 8 s.
- **Ponto de partida do stream:** 20,7 MB em dois dias porque o `tool_response` das leituras do próprio `events.jsonl` era gravado por inteiro (realimentação). Com o corte a 16 KB por campo, a mesma sessão gera uma fração disso.
